- missing equity blocks paper/live trading
- same input produces same position size
- high confidence never bypasses caps

--------------------------------------------------
STEP 6B — LEARNING SAFETY: CANDIDATE THRESHOLDS
--------------------------------------------------

Goal:

Prevent the learning loop from overfitting to recent trades.

This extends Step 6 without removing the existing learning loop.

Critical rule:

The learning layer must NOT directly modify active live thresholds
from the same data it analyzes.

This step supersedes any direct threshold update behavior from the original Step 6.

Do not delete the old Step 6 logic.

Wrap it so that any threshold update becomes a candidate threshold proposal.

Existing tests from Step 6 must still pass.

New behavior must ensure that active thresholds are modified only
through the OOS promotion gate.

All threshold changes must follow this promotion flow:

1. Analyze completed historical trades
2. Generate candidate_thresholds
3. Validate candidate_thresholds on a later out-of-sample window
   not used for discovery
4. Promote candidate_thresholds to active_thresholds only if validation passes
5. Reject candidate_thresholds if validation fails

Required files:

- active_thresholds.json
- candidate_thresholds.json
- threshold_adaptation_log.json

Rules:

- active_thresholds are used for all trading decisions
- candidate_thresholds are proposed changes only
- candidate_thresholds must never affect trading until promoted
- every promotion or rejection must be logged
- rejected candidates must not modify active thresholds
- candidate thresholds must remain bounded
- active thresholds must remain backward compatible with existing threshold structure

Promotion is allowed only if:

- out-of-sample win_rate improves or remains stable
- profit_factor improves or remains stable
- max_drawdown does not increase materially
- trade_count remains statistically meaningful
- no edge_decay_alert is active
- no kill_switch_active state exists
- validation window is strictly later than discovery window

If promotion fails:

{
  "thresholds_adapted": false,
  "reason": "candidate_rejected_oos_validation"
}

Add tests:

tests/test_candidate_thresholds.py

Tests must ensure:

- candidate thresholds do not affect active trading
- failed validation does not modify active thresholds
- successful validation promotes candidate thresholds
- promotion/rejection is logged
- thresholds remain bounded
- old Step 6 outputs remain supported
- direct threshold updates are blocked when addendum is active

--------------------------------------------------
STEP 6C — SAMPLE SIZE HARDENING
--------------------------------------------------

Goal:

Prevent learning from tiny samples.

Update attribution and adaptation minimums:

1. Confidence bucket analysis:

- default min_trades_per_bucket = 20

2. Regime analysis:

- default min_trades_per_regime = 30

3. Confidence bucket × regime cross-analysis:

- default min_trades_per_combination = 50

4. Threshold adaptation:

- never adapt before at least 100 completed trades total
- never adapt from any bucket/regime combination below its minimum

5. All minimums must be configurable, not hardcoded.

6. For unit tests only:

- smaller minimums may be injected via test config
- production/default config must remain conservative

7. If sample size is insufficient:

{
  "thresholds_adapted": false,
  "reason": "insufficient_sample_size"
}

Add tests:

tests/test_sample_size_rules.py

Tests must ensure:

- no attribution result is produced below minimum sample size
- no threshold update happens before 100 completed trades by default
- cross-analysis requires at least 50 trades per combination by default
- insufficient sample size produces clear reason
- test-injected smaller minimums do not alter production defaults

--------------------------------------------------
STEP 6D — OUT-OF-SAMPLE VALIDATION BEFORE PROMOTION
--------------------------------------------------

Goal:

Ensure the learning engine validates changes on unseen later data
before accepting them.

Tasks:

1. Split completed historical trades into:

- discovery window
- validation window

2. Candidate thresholds may be discovered only from the discovery window.

3. Candidate thresholds must be tested only on the later validation window.

4. Validation window must be strictly later in time than discovery window.

5. Reject if:

- validation window overlaps discovery window
- validation window is earlier than discovery window
- validation trade count is below minimum
- profit_factor deteriorates materially
- max_drawdown increases materially
- stability_score falls below threshold
- candidate improves win_rate but worsens risk materially
- candidate reduces trade count below meaningful threshold

6. Validation must compare:

- current active thresholds
- proposed candidate thresholds

on the same validation window.

7. Add tests:

tests/test_oos_promotion_gate.py

Tests must ensure:

- discovery and validation windows do not overlap
- validation must be later than discovery
- weak OOS result rejects candidate
- strong OOS result allows promotion
- future data is never used during discovery
- win_rate improvement alone is insufficient if drawdown worsens materially
- active thresholds remain unchanged after rejection

--------------------------------------------------
STEP 6E — PERFORMANCE CLAIM SAFETY
--------------------------------------------------

Goal:

Avoid false claims about improvement.

Replace any interpretation of:

"Win rate must improve over time — provably"

With the safer rule:

The system must measure performance over time and only accept
parameter changes that improve or preserve out-of-sample robustness.

The system must never assume that win rate will improve.

Rules:

- Do not force improvement
- Do not fabricate improvement
- Do not optimize only for win_rate
- Prefer robustness over higher win_rate
- A lower win_rate with better profit_factor and lower drawdown may be acceptable
- Any improvement claim must be supported by logged validation results
- If evidence is insufficient, report insufficient evidence
- If performance worsens, report it clearly

Add tests:

tests/test_performance_claim_safety.py

Tests must ensure:

- system can reject adaptation even after many losses
- system does not force threshold updates
- system does not claim improvement without validation evidence
- win_rate alone is not enough for promotion
- insufficient evidence produces a clear result
- rejected candidates do not produce improvement claims

--------------------------------------------------
STEP 7 — PAPER TRADING VALIDATION GATE
--------------------------------------------------

Goal:

Prevent premature live deployment.

Before live trading, system must pass paper trading validation.

Promotion to live mode is allowed only if ALL pass:

- minimum 100 completed paper trades
- profit_factor >= configured minimum, default 1.20
- max_drawdown <= configured maximum
- no lookahead bias detected
- no data leakage detected
- no active edge_decay_alert
- no active kill switch
- valid cost model exists
- valid account/equity state exists
- stable results across at least 3 market regimes if available in data

If fewer than 3 regimes exist in the validation data:

- report insufficient_regime_diversity
- do not fail silently
- allow config to decide whether this blocks live promotion

If paper validation fails:

{
  "live_enabled": false,
  "reason": "paper_validation_failed"
}

Optional detailed reason:

{
  "live_enabled": false,
  "reason": "paper_validation_failed",
  "details": string
}

Live activation rule:

Passing paper validation does not automatically enable real trading.

live_mode may execute real orders only if:

- paper validation passed
- live_enabled explicitly set to true
- kill switch is inactive
- all live safety checks pass

If live_enabled is missing or false:

{
  "trade_allowed": false,
  "reason": "live_not_explicitly_enabled"
}

Add tests:

tests/test_paper_trading_gate.py

Tests must ensure:

- live mode blocked below 100 paper trades
- live mode blocked when profit_factor too low
- live mode blocked when max_drawdown too high
- live mode blocked during edge decay
- live mode blocked during active kill switch
- live mode blocked when cost model is missing
- live mode blocked when live_enabled is missing or false
- live mode allowed only when all validation rules pass
- insufficient regime diversity is reported clearly

--------------------------------------------------
STEP 8 — LIVE SAFETY KILL SWITCH
--------------------------------------------------

Goal:

Immediately stop trading during any unsafe live condition.

System must activate kill switch if ANY of the following occurs:

- daily loss limit reached
- max consecutive losses reached
- data feed stale
- duplicate candle detected
- invalid candle detected
- abnormal slippage detected
- execution error detected
- active edge_decay_alert
- cost model missing
- account equity unavailable
- position state mismatch
- unknown system mode
- corrupted threshold config
- corrupted trade state

Abnormal slippage is defined as ANY of:

- actual_slippage > configured_max_slippage
- actual_slippage > expected_slippage * configured_slippage_multiplier

Position state mismatch is defined as ANY of:

- engine believes a position is open but account/broker state shows no position
- account/broker state has an open position not tracked by engine
- multiple open positions exist when only one is allowed
- tracked position size differs materially from actual position size
- entry price is missing for an open position

Corrupted threshold config is defined as ANY of:

- required threshold keys are missing
- any threshold value is outside its valid range
- threshold file is unreadable or inaccessible
- threshold file produces a JSON parse error
- threshold file contains non-numeric values where numeric is required
- threshold config version is missing or unsupported
- candidate threshold schema does not match active threshold schema

When kill switch is active:

{
  "trade_allowed": false,
  "reason": "kill_switch_active",
  "kill_switch_reason": string
}

Kill switch rules:

- kill switch overrides all signal and confidence logic
- kill switch cannot be bypassed by high confidence
- kill switch state must be logged with timestamp and reason
- system requires explicit safe reset before trading resumes
- kill switch state must be deterministic and inspectable
- kill switch must preserve the original reason that triggered it

--------------------------------------------------
SAFE RESET RULES
--------------------------------------------------

For live_mode:

Safe reset requires ALL of:

- manual_reset flag explicitly set to True
- all safety checks pass
- no active edge_decay_alert
- no unresolved execution error
- valid recent candle stream
- valid account/equity state
- valid cost model
- reset attempt logged with timestamp and reason

Live mode must NOT auto-reset.

For backtest_mode and paper_mode only:

Automatic reset may be allowed if ALL pass:

- last N consecutive candles are valid, default N=10
- no execution errors for X minutes or equivalent simulated period, default X=30
- no active edge_decay_alert
- valid cost model
- reset attempt logged

If reset attempt fails validation:

- kill switch remains active
- failed reset reason is logged

System cannot self-reset during active edge_decay_alert in any mode.

Add tests:

tests/test_kill_switch.py

Tests must ensure:

- confidence cannot override kill switch
- kill switch reason is preserved in output
- stale data activates kill switch
- execution error activates kill switch
- edge decay activates kill switch
- missing cost model activates kill switch in live mode
- account equity unavailable activates kill switch in live mode
- abnormal slippage activates kill switch
- position state mismatch activates kill switch
- corrupted threshold config activates kill switch
- live mode cannot auto-reset
- kill switch cannot self-reset during edge_decay_alert
- reset attempt is always logged
- system resumes only after valid reset conditions are met
